# 聊天输入区、混合附件与失败恢复设计

## 目标

修复 macOS 聊天输入区的表情弹窗裁剪、无效工具按钮和截图粘贴问题，将聊天附件从“仅图片”扩展为一条消息中的多个图片或普通文件，并补齐历史图片恢复、附件失败重传和非阻塞连续发送能力。

## 交互设计

- 表情按钮使用悬浮面板，不占用输入区固定高度；按钮再次点击关闭，选择表情后插入文本并关闭。
- 输入工具栏保留表情、附件和发送，移除剪刀、语音、抖一抖、电话、视频。
- `Cmd+V` 优先读取剪贴板中的 PNG/TIFF/NSImage；没有图片时继续执行普通文本粘贴。
- 附件选择支持多选，图片显示缩略图，普通文件显示文件图标、名称和大小；可在发送前删除单个附件。
- `Enter` 统一发送当前草稿中的文字、表情、附件、引用或它们的组合；`Shift+Enter` 插入换行。
- 中文输入法存在未确认的标记文本时，`Enter` 只确认候选文字，不触发发送。
- 输入区占位提示仅在文字、表情、附件和引用内容全部为空时显示；任一内容进入草稿后立即隐藏。
- 首次附件上传和失败附件重传都不得锁定聊天输入框。用户提交一条消息后可以立刻继续编辑并发送下一条文字或附件消息。

## 消息模型

`MIXED v2` 的 `attachments` 数组统一使用 `ChatAttachment`：

```json
{
  "kind": "file",
  "fileId": 123,
  "fileName": "资料.pdf",
  "fileSize": 45678,
  "mimeType": "application/pdf"
}
```

图片附件继续携带 `width`、`height`、`thumbnailFileId`、`previewFileId` 等可选字段。旧 `IMAGE` 与 `MIXED v1` 图片消息保持可解析。

发送方提交草稿时立即创建本地乐观消息并清空输入区。包含附件的消息交给后台传输协调器处理；批次内附件逐个上传，全部成功后发送一次 `MIXED` 消息。任何附件失败都不发送半条消息，并保留成功附件和失败附件各自的状态，支持单附件重传或删除。

## 状态与并发边界

输入草稿状态与附件传输状态必须彻底分离：

- 输入区只维护当前草稿，不再绑定历史消息的上传、重传或下载状态。
- 不再使用 `isUploadingAttachment` 同时控制输入框和后台附件任务。
- 每条包含附件的消息使用独立 `clientMsgId`、批次状态和附件状态。
- 文字消息继续通过 10086 立即发送，不等待任何附件任务。
- 附件消息提交后台队列；允许多个消息批次排队，限制同时活跃的批次数量，避免无限建立 10087 连接。
- 每个活跃批次只使用一条 10087 连接，批次内原图、缩略图、预览图和普通文件顺序复用该连接。
- 某个批次上传、失败或重传时，不改变另一个批次和输入草稿的可编辑状态。

## 连接恢复与附件重传

- Socket 断开必须同步更新真实连接状态；即使调用方不需要 UI 通知，也不能保留伪造的 `.connected` 状态。
- 批次会话重连必须等待旧流关闭，并在新流达到可写状态后才能继续发送 `RESUME_CHECK`。
- 单附件点击重传后，状态按 `failed/paused -> waiting -> uploading -> succeeded/failed` 转换，并进入后台协调器，而不是直接受输入框全局状态拦截。
- 重传优先复用原 `taskId` 和服务端断点；如果任务上下文已失效，则在保留同一附件记录的前提下重新创建有效上传会话。
- 重传前校验持久化源文件路径、实际大小和记录大小。文件不存在、文件为 0 字节或大小不一致时停止网络请求，并提示用户重新选择文件。
- 失败记录必须包含阶段信息，至少区分连接、断点检查、元数据握手、数据发送、进度 ACK、完整性校验和最终 ACK。
- 点击发生在其他附件仍上传时不得静默丢弃；重传请求应排队，或明确显示已经进入等待状态。

## 历史图片恢复

历史消息加载后，图片仍按原图、派生预览图、缩略图的顺序从服务端拉取。客户端内存预览只能用于当前本地乐观消息，不能掩盖服务端文件引用错误。

服务端 `file` 表使用预分配雪花 ID。通用 Mapper 的 `LAST_INSERT_ID()` 不得覆盖文件实体中的雪花 ID；上传最终 ACK 必须返回插入并回读成功的真实文件 ID。

已写入聊天消息的错误 `fileId` 不会因代码修复自动恢复，需要数据库修复流程：

1. 扫描 `IMAGE` 和 `MIXED` 消息中的 `fileId`、`thumbnailFileId`、`previewFileId`。
2. 找出数据库不存在、已删除或物理文件缺失的引用。
3. 仅在发送方、文件名、文件大小和上传时间能够唯一匹配时生成替换关系。
4. 更新前写入备份表；匹配不唯一的记录只输出报告，不自动修改。
5. 修复后重新校验文件表、物理文件和聊天 JSON 三者一致。

## 接收与下载

图片附件继续进入现有高清预览和缩略图链路。普通文件显示文件卡片，点击下载时复用 `TransferTaskManager` 和 `FileDownloadService`，不修改云盘下载协议。

## 服务端兼容

`ChatAttachmentContentValidator` 对 `MIXED` 附件同时允许 `image` 和 `file`，统一校验文件存在、发送方归属、文件名和文件大小；图片专有派生字段仍按可选字段校验。旧图片消息规则不变，数量上限继续为 9。

消息发送校验失败时，回执需要返回可识别的附件字段和 `fileId`。客户端收到“附件不存在、归属错误或大小不匹配”后，应将对应附件降级为失败状态，不能把所有附件继续视为上传成功并反复发送同一份无效 JSON。

## 验收标准

- 重启客户端并进入聊天后，服务端存在的历史图片可以自动显示并打开高清预览。
- 历史错误引用经过数据库修复后，发送方和接收方都可重新加载图片。
- 一个附件失败不会让同批次后续附件因伪连接状态连续报“Socket 未连接”。
- 单附件重传可以排队并最终更新该附件状态，不影响输入框编辑和新消息发送。
- 一个附件批次上传期间，可以连续发送文字消息和新的附件消息。
- `Enter` 可发送纯文字、纯表情、纯附件以及混合内容；`Shift+Enter` 可换行；中文输入法确认候选词不会误发送。
- placeholder 在草稿出现文字、表情、附件或引用后立即消失，草稿完全清空后恢复。
- 0 字节、丢失或大小变化的源文件不会发起无效上传，并给出可操作提示。
- 云盘上传下载仍走原有任务与连接管理，不受聊天附件协调器影响。

## 风险与边界

- 附件数量上限保持 9，避免单条消息过大。
- 允许的普通文件类型沿用文件上传服务能力，不在客户端硬编码窄名单；服务端仍可按业务策略拒绝危险类型。
- 不改变云盘列表、普通文件上传下载和已有图片消息的存储格式。
- 不自动修复无法唯一匹配的历史附件记录。
- 本轮实现完成后不由 Codex 编译或执行测试，交由用户按验收标准自行验证。
