# 聊天历史非阻塞窗口设计

## 目标

聊天历史读取、增量同步、内容解析、排序合并和图片解码不得阻塞 SwiftUI 主线程。无论单个好友有多少历史记录，聊天页面只渲染固定上限的消息窗口，并能向前、向后从本地数据库分页移动。

## 数据流

1. Core Data 保存完整历史，是历史分页的事实来源。
2. `SocketManager.chatHistory[friendId]` 只保存当前会话的可见窗口，默认最多 160 条。
3. 进入会话读取本地最新页；网络增量同步逐页落库，但合并完成后只向 UI 发布一次。
4. 向上到达窗口边界时读取更早本地页；本地边界耗尽后才请求服务端。
5. 窗口因加载更早消息而裁掉较新消息时，标记 `hasNewer`；向下到达窗口边界时从本地读取较新页。
6. 排序、去重、裁剪和消息载荷解析在后台完成；主线程只替换最多 160 条已经准备好的消息数组。

## 渲染约束

- 时间线最多处理 160 条消息，避免历史总量影响 SwiftUI 布局成本。
- 消息 JSON 载荷在 `ChatMessage` 创建或内容更新时解析一次，`body` 不重复调用 `JSONDecoder`。
- 普通消息不启用 `.textSelection(.enabled)`；复制继续通过右键菜单完成。
- 聊天气泡只自动加载派生缩略图或派生预览图。二者都不存在时显示占位图，原图仅在用户点击预览后拉取。
- 历史分页恢复滚动位置使用明确的窗口修订号，不监听消息总数；窗口达到上限后数量不变也必须能恢复位置。

## 存储约束

- 新增 `(accountId, friendId, messageId)` 复合索引，避免本地游标分页为排序创建临时 B-Tree。
- 新增本地 `fetchNewer` 游标分页，供窗口向较新方向移动。
- 所有 Core Data 读写继续使用后台 Context。

## 验收

- 窗口策略、双向本地分页、批量增量发布、图片源选择和预解析载荷均有自动化测试。
- 专项测试与完整 macOS 构建通过。
- 真实客户端连续上下滚动时，不自动拉取缺少派生缩略图的原图，不出现主线程同步数据库、排序、JSON 解析或图片解码。
