# 在线拉流播放 — 问题分析与优化方案

> 记录日期：2026-04-20
> 项目：chat-storage（macOS 客户端）

---

## 一、整体架构说明

```
AVPlayer
  │ HTTP Range 请求（bytes=startOffset-endOffset）
  ▼
LocalMediaServer（本地 HTTP 代理，NWListener，端口随机分配）
  │
  ├─ 路径1：目标区间已在磁盘缓存命中  → 直接读盘，立即响应
  ├─ 路径2：顺序小幅未命中            → 注册 RangeWaiter，等后台流写到目标位置后自动唤醒
  └─ 路径3：大幅 seek / 向后跳 / 超大区间 → 创建专用 VideoStreamingService，向服务端发 range_pull 请求
               │
               ▼
VideoStreamingService（独立 SocketManager，连接端口 10088）
  │ 自定义 Socket 协议帧：metaFrame（请求）→ dataFrame（数据流）→ endFrame（结束）
  │ 请求体：{ op: "range_pull", fileId, startOffset, length, taskId, requestId }
  ▼
远程服务端（Java NIO，端口 10088）
  │ 按 startOffset + length 窗口化返回视频字节流
  ▼
后台流写入 VideoStreamCache（临时磁盘文件 video_{fileId}.cache）
  │ 写入后唤醒对应 RangeWaiter
  ▼
LocalMediaServer 读盘 → HTTP 206 Partial Content 响应给 AVPlayer
```

---

## 二、进度条拖动完整触发链路

```
用户松开进度条（onEnded）
  │
  ▼
StreamingVideoViewModel.seekToFraction(fraction)
  │ player.seek(to: targetTime, toleranceBefore: .zero, toleranceAfter: 0.5s)
  ▼
AVPlayer 内部取消当前缓冲请求，发出新 HTTP Range 请求
  │ GET /stream?fileId=xxx&size=xxx&name=xxx
  │ Range: bytes=targetOffset-endOffset
  ▼
LocalMediaServer.processRequest() → streamVideoData()
  │ 根据 startOffset 与 cache.currentDownloadPosition 的距离决策路径
  │
  ├─ gap < catchUpThreshold（后台流能在 Waiter 超时内追到）→ 路径2：RangeWaiter
  └─ gap >= catchUpThreshold 或向后跳 或超大区间              → 路径3：专用流
```

## 三、当前存在的问题与优化方案

---

### 问题1：seek 阈值固定 50MB，与 Waiter 超时逻辑不闭合

**所在文件**：`LocalMediaServer.swift` → `streamVideoData()`

**问题描述**：

当前代码中，判断是否走路径3（专用拉流）的阈值为固定 50MB：

```swift
let seekThreshold: Int64 = 50 * 1024 * 1024
let isLargeForwardJump = startOffset > currentPos && (startOffset - currentPos) >= seekThreshold
```

而 RangeWaiter 的超时时间为 20 秒（`defaultTimeoutSeconds = 20.0`）。这两个值之间没有逻辑关联，导致：

- 跳转距离 < 50MB 但后台流在 20 秒内追不到目标位置的情况（如跳转 30MB，网速 500KB/s），会进入 Waiter 等待，但 20 秒后必然超时，Waiter 调用 `cancel()` 直接关闭 NWConnection，AVPlayer 收到连接关闭信号，触发 `.AVPlayerItemFailedToPlayToEndTime`，播放中断

**优化方案**：

将阈值改为与 Waiter 超时时间动态对齐，以"后台流在 Waiter 超时时间内是否能追上"为判断标准：

```swift
// LocalMediaServer.swift — streamVideoData() 方法中

let currentPos = cache.currentDownloadPosition
let isBackwardAccess = startOffset < cache.downloadStartOffset

// 以保守网速 1MB/s 估算：Waiter 超时 20s 最多能等后台流追上 20MB
// 超过 20MB 的跳转，后台流在超时窗口内追不上，必须走专用流
let catchUpThreshold: Int64 = 20 * 1024 * 1024  // 20MB，与 Waiter 超时 20s × 1MB/s 对齐
let isLargeForwardJump = startOffset > currentPos && (startOffset - currentPos) >= catchUpThreshold

// 超过 10MB 的单次 Range 请求（如 moov 探针、全文件请求）走专用流
// 避免 Waiter 必须等全文件缓存完才能触发（实际永远不触发，20s 后超时）
let rangeSize = endOffset - startOffset + 1
let isVeryLargeRange = rangeSize > 10 * 1024 * 1024

let needsDedicatedStream = isBackwardAccess || isLargeForwardJump || isVeryLargeRange
```

**边界说明**：
- `catchUpThreshold = 20MB`：保守按 1MB/s 网速，20s × 1MB/s = 20MB，超过此距离 Waiter 一定超时
- `isVeryLargeRange > 10MB`：单次请求超过 10MB 说明是全文件级别请求，不适合 Waiter 等待模式
- 向后跳（`startOffset < downloadStartOffset`）：后台流只向前写，必须走专用流重启

### 问题2：Waiter 超时后直接关闭连接，无降级处理

**所在文件**：`VideoStreamCache.swift` → `notifyWaiters()`

**问题描述**：

当 Waiter 超时时，当前直接调用 `cancel()` 关闭 NWConnection：

```swift
} else if now > waiter.timeoutAt {
    waiter.cancel()  // 直接关闭连接，AVPlayer 触发错误
}
```

这会导致 AVPlayer 收到连接关闭，触发播放失败回调，而不是触发一次重试或降级到专用流。

**优化方案**：

为 `RangeWaiter` 增加 `fallback` 回调，超时时优先降级到路径3（专用拉流），只有 fallback 不存在时才 cancel：

**第一步**：修改 `RangeWaiter` 结构体，增加 `fallback` 字段：

```swift
// VideoStreamCache.swift
private struct RangeWaiter {
    let range: ClosedRange<Int64>
    let serve: () -> Void
    let cancel: () -> Void
    let fallback: (() -> Void)?   // 新增：超时降级回调，优先于 cancel
    let timeoutAt: Date

    static let defaultTimeoutSeconds: Double = 20.0
}
```

**第二步**：修改 `notifyWaiters()` 超时处理逻辑：

```swift
// VideoStreamCache.swift — notifyWaiters()
private func notifyWaiters() {
    guard !waiters.isEmpty else { return }
    let now = Date()
    var remaining: [RangeWaiter] = []
    for waiter in waiters {
        if isRangeAvailableUnsafe(waiter.range) {
            waiter.serve()
            // serve 后不再保留，已满足
        } else if now > waiter.timeoutAt {
            // 超时：优先调用 fallback（降级到专用流），无 fallback 才 cancel
            if let fallback = waiter.fallback {
                fallback()
            } else {
                waiter.cancel()
            }
            // 超时 Waiter 不再保留
        } else {
            remaining.append(waiter)
        }
    }
    waiters = remaining
}
```

**第三步**：`LocalMediaServer` 注册 Waiter 时传入 fallback，降级到专用流：

```swift
// LocalMediaServer.swift — streamVideoData() 路径2注册 Waiter 处

let fallback: () -> Void = { [weak self, weak connection] in
    guard let self, let connection else { return }
    self.queue.async {
        // 降级：以相同参数走路径3专用流
        print("⚡ [LocalMediaServer] Waiter 超时，降级专用流: bytes=\(startOffset)-\(endOffset)")
        self.createDedicatedStream(
            fileId: fileId,
            startOffset: startOffset,
            endOffset: endOffset,
            to: connection
        )
    }
}

cache.registerWaiter(
    for: startOffset...endOffset,
    serve: serve,
    cancel: { connection.cancel() },
    fallback: fallback   // 传入降级回调
)
```

**第四步**：同步更新 `registerWaiter` 方法签名：

```swift
// VideoStreamCache.swift
func registerWaiter(
    for range: ClosedRange<Int64>,
    serve: @escaping () -> Void,
    cancel cancelCallback: @escaping () -> Void,
    fallback: (() -> Void)? = nil   // 新增可选参数，默认为 nil 向后兼容
) {
    let waiter = RangeWaiter(
        range: range,
        serve: serve,
        cancel: cancelCallback,
        fallback: fallback,
        timeoutAt: Date().addingTimeInterval(RangeWaiter.defaultTimeoutSeconds)
    )
    cacheIOQueue.async { [weak self] in
        guard let self else { cancelCallback(); return }
        self.waiters.append(waiter)
        self.notifyWaiters()
    }
}
```

**边界说明**：
- `fallback` 为可选参数，默认 nil，不影响现有调用方（`restartDownloadAndRegisterWaiter` 内部注册的 Waiter 不需要 fallback，直接 cancel 即可）
- fallback 执行时连接仍然存活，专用流会向同一个 NWConnection 写数据，逻辑与路径3完全一致
- fallback 和 cancel 互斥，超时只会调用其中一个

### 问题3：多次快速 seek 积压旧 Waiter，触发多次连接关闭

**所在文件**：`StreamingVideoViewModel.swift` → `seekToFraction()`、`VideoStreamCache.swift`

**问题描述**：

用户快速拖动进度条到 A 点松手，Waiter_A 注册；立刻又拖到 B 点松手，Waiter_B 注册。两个 Waiter 同时存在于 `waiters` 数组中，各自 20 秒超时倒计时，最终先后 cancel 关闭连接，AVPlayer 收到两次连接关闭，表现为两次播放错误。

**优化方案**：

在 `seekToFraction` 调用时，先清除当前文件的所有旧 Waiter，再让 AVPlayer 发出新 Range 请求。

**第一步**：`VideoStreamCache` 暴露取消所有 Waiter 的接口：

```swift
// VideoStreamCache.swift
/// 取消并清除所有等待中的 Waiter（用于新 seek 时清理旧等待）。
func cancelAllPendingWaiters() {
    cacheIOQueue.async { [weak self] in
        guard let self else { return }
        let old = self.waiters
        self.waiters = []
        print("🗑 [VideoStreamCache] 清除旧 Waiter 数量: \(old.count)")
        old.forEach { $0.cancel() }
    }
}
```

**第二步**：`VideoStreamCacheManager` 透传接口：

```swift
// VideoStreamCacheManager.swift
func cancelPendingWaiters(fileId: Int64) {
    lock.lock()
    let cache = caches[fileId]
    lock.unlock()
    cache?.cancelAllPendingWaiters()
}
```

**第三步**：`seekToFraction` 调用前先清除旧 Waiter：

```swift
// StreamingVideoViewModel.swift
func seekToFraction(_ fraction: Double) {
    guard let player, duration > 0 else { return }

    // 清除旧 Waiter，防止积压多次超时触发连接关闭
    if let fileId = currentFileId {
        VideoStreamCacheManager.shared.cancelPendingWaiters(fileId: fileId)
    }

    let targetSeconds = fraction * duration
    let targetTime = CMTime(seconds: targetSeconds, preferredTimescale: 600)
    isSeeking = true
    sliderPosition = fraction

    player.seek(
        to: targetTime,
        toleranceBefore: .zero,
        toleranceAfter: CMTime(seconds: 0.5, preferredTimescale: 600)
    ) { [weak self] finished in
        guard let self else { return }
        DispatchQueue.main.async {
            self.isSeeking = false
            if finished && self.playState == .playing {
                self.player?.playImmediately(atRate: 1.0)
            }
        }
    }
}
```

**边界说明**：
- `cancelAllPendingWaiters` 通过 `cacheIOQueue.async` 异步执行，不阻塞主线程
- cancel 调用的是每个 Waiter 的 `cancel()` 闭包，该闭包在 `LocalMediaServer` 注册时传入为 `connection.cancel()`，即关闭对应 NWConnection
- 此时 AVPlayer 已经向新的 Range 请求位置发起了请求，旧连接关闭不影响新连接
- 若旧 Waiter 的 fallback 存在，此处也应调用 cancel 而非 fallback，因为这是主动 seek 取消，不是超时降级

### 问题4：进度条松手后 seek 响应慢（路径3 需等建连）

**所在文件**：`StreamingVideoViewModel.swift`、`LocalMediaServer.swift`

**问题描述**：

当 seek 目标位置需要走路径3时，流程为：

1. `VideoStreamingService.connectIfNeeded()` → 轮询等待 Socket 连接就绪（最长 5 秒）
2. 发送 `range_pull` 请求帧
3. 等待服务端响应 `metaFrame` + 第一个 `dataFrame`

这段时间 AVPlayer 处于 `waitingToPlayAtSpecifiedRate` 状态，用户看到转圈，无法感知进度。

**优化方案**：

在用户松开进度条（`onEnded`）时，**同步触发后台预热**，在 AVPlayer 发出 Range 请求之前就开始建立 `VideoStreamingService` 连接。

**第一步**：`LocalMediaServer` 增加预热接口：

```swift
// LocalMediaServer.swift
/// 进度条松手时调用，提前判断 seek 目标是否需要走路径3，若需要则预热连接。
/// 此方法异步执行，不阻塞调用线程。
func prefetchForSeek(fileId: Int64, targetOffset: Int64, fileSize: Int64) {
    queue.async { [weak self] in
        guard let self else { return }

        let cache = VideoStreamCacheManager.shared.cache(for: fileId)

        // 判断是否需要走路径3（与 streamVideoData 中的判断逻辑保持一致）
        let needsDedicated: Bool
        if let cache, !cache.isInvalid {
            let currentPos = cache.currentDownloadPosition
            let catchUpThreshold: Int64 = 20 * 1024 * 1024
            let isBackward = targetOffset < cache.downloadStartOffset
            let isLargeJump = targetOffset > currentPos &&
                              (targetOffset - currentPos) >= catchUpThreshold
            needsDedicated = isBackward || isLargeJump
        } else {
            needsDedicated = true
        }

        guard needsDedicated else { return }

        // 提前重启后台流到目标位置，建立 Socket 连接
        // serve 和 cancel 为空闭包：预热只建连，不负责向 AVPlayer 推数据
        // 真正的数据推送由 AVPlayer 发 Range 请求后触发的 createDedicatedStream 负责
        print("🔥 [LocalMediaServer] 预热 seek 目标: offset=\(targetOffset)")
        cache?.restartDownloadAndRegisterWaiter(
            from: targetOffset,
            for: targetOffset...(min(targetOffset + 512 * 1024, fileSize - 1)),
            serve: { /* 预热专用，serve 为空 */ },
            cancel: { /* 预热专用，cancel 为空 */ }
        )
    }
}
```

**第二步**：`seekToFraction` 调用时触发预热（在清除旧 Waiter 之后）：

```swift
// StreamingVideoViewModel.swift
func seekToFraction(_ fraction: Double) {
    guard let player, duration > 0 else { return }

    let targetSeconds = fraction * duration
    let targetOffset = fileSize > 0 ?
        Int64(fraction * Double(fileSize)) : 0

    // Step 1：清除旧 Waiter
    if let fileId = currentFileId {
        VideoStreamCacheManager.shared.cancelPendingWaiters(fileId: fileId)
    }

    // Step 2：预热 seek 目标位置的连接（异步，不阻塞 seek 流程）
    if let fileId = currentFileId, fileSize > 0 {
        LocalMediaServer.shared.prefetchForSeek(
            fileId: fileId,
            targetOffset: targetOffset,
            fileSize: fileSize
        )
    }

    // Step 3：原有 AVPlayer seek 逻辑
    isSeeking = true
    sliderPosition = fraction
    let targetTime = CMTime(seconds: targetSeconds, preferredTimescale: 600)
    player.seek(
        to: targetTime,
        toleranceBefore: .zero,
        toleranceAfter: CMTime(seconds: 0.5, preferredTimescale: 600)
    ) { [weak self] finished in
        guard let self else { return }
        DispatchQueue.main.async {
            self.isSeeking = false
            if finished && self.playState == .playing {
                self.player?.playImmediately(atRate: 1.0)
            }
        }
    }
}
```

ViewModel 需要持有 `fileSize`，在 `setupPlayer` 时保存：

```swift
// StreamingVideoViewModel.swift
private var fileSize: Int64 = 0

func setupPlayer(fileId: Int64, fileName: String, expectedSize: Int64) {
    // ...
    self.fileSize = expectedSize
    // ...
}
```

**边界说明**：
- 预热的 `restartDownloadAndRegisterWaiter` 注册的是一个 serve/cancel 均为空的哑 Waiter，其唯一作用是触发后台流从 `targetOffset` 重启，不负责响应任何 NWConnection
- 当 AVPlayer 真正发出 Range 请求时，`streamVideoData` 仍然走正常的路径1/2/3决策，不依赖预热结果
- 若预热与真实请求并发，`restartDownloadAndRegisterWaiter` 内部会先取消所有旧 Waiter 并重建临时文件，是原子操作，不存在竞态
- 预热只在 `needsDedicated == true` 时触发，小幅 seek（Waiter 能等到的情况）不预热，避免无意义的连接重启

### 问题5：Chase Time 缺失，快速连续点击进度条触发并发 seek

**所在文件**：`StreamingVideoViewModel.swift` → `seekToFraction()`

**问题描述**：

用户在 `player.seek` 的 `completionHandler` 回调前多次调用 `seekToFraction`，会产生多个并发的 `player.seek` 调用。AVPlayer 内部会取消前一次 seek，但已经触发的 `LocalMediaServer` 路径决策和 Waiter 注册无法自动取消，导致资源浪费和潜在的连接混乱。

**优化方案**：

实现 Chase Time 模式，保证同一时间只有一个活跃的 `player.seek`：

```swift
// StreamingVideoViewModel.swift

private var chaseTime: CMTime = .zero        // 最新的目标时间
private var isSeekInProgress: Bool = false   // 是否有正在执行的 seek

/// 进度条松手时调用的入口，支持 Chase Time 防抖。
func seekToFraction(_ fraction: Double) {
    guard let player, duration > 0 else { return }

    let targetSeconds = fraction * duration
    let targetOffset = fileSize > 0 ? Int64(fraction * Double(fileSize)) : 0
    let targetTime = CMTime(seconds: targetSeconds, preferredTimescale: 600)

    // 更新目标时间（始终记录最新目标）
    chaseTime = targetTime
    sliderPosition = fraction

    // 清除旧 Waiter
    if let fileId = currentFileId {
        VideoStreamCacheManager.shared.cancelPendingWaiters(fileId: fileId)
    }

    // 预热连接
    if let fileId = currentFileId, fileSize > 0 {
        LocalMediaServer.shared.prefetchForSeek(
            fileId: fileId,
            targetOffset: targetOffset,
            fileSize: fileSize
        )
    }

    // 若已有 seek 在进行，只更新 chaseTime，不重复发起
    guard !isSeekInProgress else { return }

    performChaseSeek(player: player)
}

/// 递归执行 seek，直到 chaseTime 不再变化。
private func performChaseSeek(player: AVPlayer) {
    isSeekInProgress = true
    isSeeking = true
    let target = chaseTime

    player.seek(
        to: target,
        toleranceBefore: .zero,
        toleranceAfter: CMTime(seconds: 0.5, preferredTimescale: 600)
    ) { [weak self] finished in
        guard let self else { return }
        DispatchQueue.main.async {
            if CMTimeCompare(self.chaseTime, target) != 0 {
                // 目标时间在 seek 过程中已更新，继续追最新目标
                self.performChaseSeek(player: player)
            } else {
                // 已到达最新目标
                self.isSeekInProgress = false
                self.isSeeking = false
                if finished && self.playState == .playing {
                    player.playImmediately(atRate: 1.0)
                }
            }
        }
    }
}
```

**边界说明**：
- `chaseTime` 和 `isSeekInProgress` 均在 `DispatchQueue.main` 上读写，无需额外加锁
- `performChaseSeek` 递归调用时，`chaseTime` 已是最新值，每次递归都会清除旧 Waiter 并预热新目标（因为 `seekToFraction` 每次更新 `chaseTime` 时都已执行了这两步）
- 若 seek 被取消（`playState` 变为 `stopped`），`completionHandler` 中 `finished == false`，此时不恢复播放，也不继续追
- 不存在无限递归：每次递归都会让 `chaseTime == target`，下一次必然退出

### 问题6：`connectIfNeeded` 在 MainActor 上轮询，连接就绪感知低效

**所在文件**：`VideoStreamingService.swift` → `connectIfNeeded()`

**问题描述**：

```swift
await MainActor.run {
    self.socketManager.connect(host: host, port: port)
}
var attempts = 0
while attempts < 50 {           // 轮询最多 5 秒（50 × 100ms）
    if isSocketReadyForStreaming() { return }
    attempts += 1
    try? await Task.sleep(nanoseconds: 100_000_000)
}
throw SocketError.timeout
```

使用 `while` 轮询 + `Task.sleep` 检查连接状态，每次判断间隔 100ms，最坏情况下比实际连接就绪晚感知最多 100ms，且无法提前响应连接失败。

注意：`socketManager.connect()` 内部使用 `CFStreamCreatePairWithSocketToHost` + RunLoop 注册，**必须在主线程执行**，`await MainActor.run` 这部分不能移除。

**优化方案**：

保留 `MainActor.run` 执行 connect，改轮询为 Combine 状态订阅：

```swift
// VideoStreamingService.swift
import Combine

private var connectionCancellable: AnyCancellable?

private func connectIfNeeded() async throws {
    if isSocketReadyForStreaming() { return }

    // 确保旧连接已断开
    if socketManager.connectionState == .connected {
        socketManager.disconnect(notifyUI: false)
    }

    // connect 必须在主线程执行（RunLoop 注册要求）
    await MainActor.run {
        self.socketManager.connect(host: targetHost, port: targetPort)
    }

    // 改：Combine 订阅状态，第一时间感知连接就绪或失败
    try await withCheckedThrowingContinuation { (cont: CheckedContinuation<Void, Error>) in
        var isContinuationResumed = false

        connectionCancellable = socketManager.$connectionState
            .dropFirst()  // 忽略初始值（连接中状态）
            .filter { state in
                state == .connected || {
                    if case .error = state { return true }
                    return false
                }(state)
            }
            .first()
            .receive(on: DispatchQueue.global())
            .sink { [weak self] state in
                guard !isContinuationResumed else { return }
                isContinuationResumed = true
                self?.connectionCancellable = nil
                if state == .connected {
                    cont.resume()
                } else if case .error(let msg) = state {
                    cont.resume(throwing: DirectoryError.serverError(code: -1, message: msg))
                }
            }

        // 5 秒超时兜底
        Task {
            try? await Task.sleep(nanoseconds: 5_000_000_000)
            guard !isContinuationResumed else { return }
            isContinuationResumed = true
            self.connectionCancellable?.cancel()
            self.connectionCancellable = nil
            cont.resume(throwing: SocketError.timeout)
        }
    }
}
```

**边界说明**：
- `isContinuationResumed` 标志防止 Combine sink 和超时 Task 同时 resume 同一个 continuation（resume 两次会触发 Fatal Error）
- `connectionCancellable` 在 resume 后立即置 nil，确保订阅释放
- `socketManager.$connectionState` 是 `@Published` 属性，发布在主线程，`.receive(on: DispatchQueue.global())` 将 sink 调度到后台，不阻塞主线程
- 若 `VideoStreamingService` 在等待期间被 `cancel()`，Swift Task 取消机制会中断 `withCheckedThrowingContinuation`，Combine 订阅在 `deinit` 时随 `connectionCancellable` 一起释放

### 问题7：`sendFrame` 同步 sleep 阻塞调用线程

**所在文件**：`VideoStreamingService.swift` → `startCustomVideoStreaming()`

**问题描述**：

```swift
let requestFrame = Frame(type: .metaFrame,  requestData, flags: 0x00)
try self.socketManager.sendFrame(requestFrame)  // 使用同步版本
```

`sendFrame` 内部在发送缓冲区满时执行 `Thread.sleep(forTimeInterval: 0.005)`，阻塞当前线程 5ms，虽然短暂，但在 Swift async 上下文中调用同步阻塞操作会占用 cooperative thread pool 的线程资源。`sendFrameAsync` 已存在且使用 `Task.sleep` 避免了阻塞。

**优化方案**：

直接替换为异步版本：

```swift
// VideoStreamingService.swift — startCustomVideoStreaming() 中注册 handler 后

let requestFrame = Frame(type: .metaFrame,  requestData, flags: 0x00)
do {
    try await self.socketManager.sendFrameAsync(requestFrame)  // 改为异步版本
} catch {
    self.complete(.failure(error))
}
```

**边界说明**：
- `sendFrameAsync` 与 `sendFrame` 行为完全等价，只是将 `Thread.sleep` 替换为 `await Task.sleep`，不影响发送语义
- 已在 `withCheckedThrowingContinuation` 的 handler 注册完成后再发送请求帧，时序不变，不引入竞态

### 问题8：`endFrame` 帧类型语义歧义（服务端协议问题）

**所在文件**：`VideoStreamingService.swift`（客户端兼容代码）、服务端 Java NIO 协议层

**问题描述**：

服务端有时将最后一个数据块用 `END_FRAME` 帧类型发送，导致客户端需要通过猜测 payload 内容来区分"数据帧"和"结束控制帧"：

```swift
case .endFrame:
    let looksLikeControlEnd = dict["status"] != nil || dict["totalBytes"] != nil || ...
    if !looksLikeControlEnd {
        // 按数据帧处理
    }
```

此逻辑脆弱，服务端协议稍有变动就可能导致误判。

**服务端修复方案（Java NIO）**：

严格区分帧类型语义：

- `DATA_FRAME`：payload 必须是纯视频字节流，不携带任何 JSON 字段
- `END_FRAME`：payload 必须是 JSON 控制信息（如 `{"status":"ok","totalBytes":xxx}`），绝不携带视频数据

服务端在发送最后一块数据时，必须先发一个 `DATA_FRAME` 帧携带数据，再发一个 `END_FRAME` 帧携带结束信息，不能合并为一帧。

**客户端过渡策略**：

在服务端修复上线之前，客户端现有的兼容代码保留，但判断条件改为更显式的格式检测，减少误判：

```swift
case .endFrame:
    // 优先尝试解析为 JSON 控制帧
    if let jsonString = String( frame.data, encoding: .utf8),
       let jsonData = jsonString.data(using: .utf8),
       let dict = try? JSONSerialization.jsonObject(with: jsonData) as? [String: Any],
       dict["status"] != nil || dict["totalBytes"] != nil ||
       dict["sentBytes"] != nil || dict["eof"] != nil || dict["message"] != nil {
        // 明确是控制帧，处理结束逻辑
        if let status = dict["status"] as? String, status == "error" || status == "fail" {
            let msg = dict["message"] as? String ?? "服务端错误"
            let error = DirectoryError.serverError(code: -1, message: msg)
            delegate.didFail(with: error)
            self.complete(.failure(error))
            return false
        }
        delegate.didFinishLoading()
        self.complete(.success(()))
        return false
    } else {
        // payload 不是合法 JSON 控制信息，按数据帧兼容处理
        let data = frame.data
        let range = receivedSize..<(receivedSize + Int64(data.count))
        delegate.didReceiveVideoData(data, range: range)
        receivedSize += Int64(data.count)
        receivedBytesInWindow += Int64(data.count)
        return !self.currentlyCancelled
    }
```

**边界说明**：
- 服务端修复是根本解决方案，客户端兼容代码在服务端修复并灰度验证完成后可删除
- 判断顺序：先尝试 JSON 解析，成功且包含控制字段 → 控制帧；否则 → 数据帧。不存在"两种都算"的歧义路径

### 问题9：seek 缓冲期间 UI 无区分，用户体验差

**所在文件**：`StreamingVideoPlayer.swift`、`StreamingVideoViewModel.swift`

**问题描述**：

seek 后 AVPlayer 进入 `waitingToPlayAtSpecifiedRate` 状态，与正常起播缓冲显示相同的"缓冲中..."转圈，用户无法区分是在等待 seek 结果还是起播缓冲，体验模糊。

**优化方案**：

在 ViewModel 中增加 `isSeekBuffering` 状态，UI 层区分显示。

**ViewModel**：

```swift
// StreamingVideoViewModel.swift
@Published var isSeekBuffering: Bool = false

// 在 performChaseSeek 开始时设为 true
private func performChaseSeek(player: AVPlayer) {
    isSeekInProgress = true
    isSeeking = true
    isSeekBuffering = true   // 标记进入 seek 缓冲
    let target = chaseTime

    player.seek(to: target, toleranceBefore: .zero,
                toleranceAfter: CMTime(seconds: 0.5, preferredTimescale: 600)) { [weak self] finished in
        guard let self else { return }
        DispatchQueue.main.async {
            if CMTimeCompare(self.chaseTime, target) != 0 {
                self.performChaseSeek(player: player)  // 继续追，isSeekBuffering 保持 true
            } else {
                self.isSeekInProgress = false
                self.isSeeking = false
                self.isSeekBuffering = false   // seek 到位，退出 seek 缓冲状态
                if finished && self.playState == .playing {
                    player.playImmediately(atRate: 1.0)
                }
            }
        }
    }
}
```

**View 层**：

```swift
// StreamingVideoPlayer.swift — 缓冲提示区域
if viewModel.isLoading {
    VStack(spacing: 8) {
        ProgressView().scaleEffect(1.5)
        Text(viewModel.isSeekBuffering ? "跳转中..." : "缓冲中...")
            .foregroundColor(.white)
            .font(.caption)
    }
    .padding()
    .background(Color.black.opacity(0.6))
    .cornerRadius(10)
}
```

**边界说明**：
- `isSeekBuffering` 仅用于 UI 文案区分，不影响任何播放逻辑
- `isLoading` 由 `player.timeControlStatus == .waitingToPlayAtSpecifiedRate` 驱动（AVPlayer KVO），`isSeekBuffering` 由 ViewModel seek 状态机驱动，两者独立，不存在状态覆盖问题
- seek 完成（`performChaseSeek` 退出递归）时 `isSeekBuffering` 置 false，即使 AVPlayer 仍在缓冲（`isLoading` 仍为 true），UI 会从"跳转中"切换为"缓冲中"，语义正确
